# F1. Local recording and scrape example

[Worklist](../metrics-transducer-worklist.md) | [UDP codecs](e1.md) |
[HTTP pull](e2.md)

The deliverable is a runnable, single-core example with a fixture sender,
configuration, expected decoded samples and restart instructions. Its user
should be able to answer "did my two counter updates survive a scrape and a
restart?" without inspecting a checkpoint file.

## Topology and responsibilities

```text
UDP DogStatsD v1.1 -> receiver:statsd -> edge A -> committed pull reader
                                                        |
                                      HTTP GET /metrics (Prometheus text)
```

Configure a Linux [state directory][state-dir], a stable writer identity, a
one-minute UTC grid, sealed-only results and enough retention for the
exercise. Keep the fixture ports separate from the admin endpoint. The UDP
node carries the original bytes with their configured encoding. The rule
selects the `requests` counter and retains the **point** attribute `service`;
the pull reader requests its cumulative representation. The example must
publish its name/unit translation so users know which series to look for.

## Procedure and expected results

1. Start with a new state namespace and wait for listener readiness. In
   one open interval send `requests:3:4|c|#service:api`. Wait for the
   receiver's accepted input position and for the commit sealing that
   interval. A successful UDP send alone proves neither.
2. Scrape `/metrics` twice at that commit. Parse the responses: the selected
   `service="api"` series has value **7** and the counter type. Scraping
   must leave the epoch start and push-reader position unchanged. Also read
   the same commit using the `otlp-bytes` route and compare decoded values.
3. Stop and restart with the same state namespace and rule generation. Wait
   for recovery before reading. Without resending the packet, the result
   must still be **7**, not absent, zero or 14.
4. Repeat in a fresh namespace with `requests:3|c|#service:api` and
   `requests:4|c|#service:api`. Both lines belong to the same window and
   produce the same series. [E1](e1.md) separately covers plain StatsD
   round trips; DogStatsD tags and packing are intentional here.

Include two typed cases, with explicit mappings: an additive non-monotonic
level moving from 7 to 4 has an interval change of -3; a temperature gauge
moving from 7 to 4 has latest value 4. A wire gauge token alone cannot
choose between them.

## Query milestone

Ship the fixed-rule example first. As soon as one [query front end](e6.md)
can express the same native count aggregation, run that rule over the same
accepted fixture and require the same 7, labels and restart behavior. This
is a small end-to-end gate for a real rule, independent of how much PromQL
or OPL syntax the compiler can parse. A fixture runner should drive ingress
time and seal notifications explicitly; manual scrape times are illustrative.
