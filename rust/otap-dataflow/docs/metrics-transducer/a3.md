# A3. Deterministic reference evaluator and fixtures

[Worklist](../metrics-transducer-worklist.md) | [Query-time comparison](e6d.md)

The oracle answers: *given this prefix of accepted input and these seal
decisions, what should a reader see?* It must work before Quiver, sockets or
the production query compiler exist. Agreement between two executors using
the same incorrect plan is not a substitute for a known expected answer.

## Fixture contract

Use an ordered script of observations, writer progress, seal/cutoff events
and reader operations. Each observation carries a writer, full input series,
kind, temporality, value or no-data marker, start (possibly absent) and event
time. Give publications explicit keys when exercising the regional link.
Keep delivery order separate from event time. A fixture states the rule
generation, time grid, finite limits and late-data policy it uses.

The output is a sequence of logical commits: covered input positions,
sealed-through boundary, completeness, and output cells with their
descriptors, epochs and values. Reader expectations identify the commit
being read. Compare logical series, not Arrow row order, segment numbers or
the wall time of a scrape. Rejections, duplicates, gaps and incompleteness
are observable outputs. A missing series is distinct from a measured zero.

## Reference architecture

Start with a small in-memory interpreter over the fixed [A1](a1.md) rule.
It can keep the entire finite fixture, sort by contributor and event time,
and recompute the expected window from first principles. Resolve epochs
before projection. Use the same input schema and policies as the incremental
evaluator but keep the arithmetic and seal decisions independently checkable.
Record hand-derived expected values alongside the script.

Replay the script into direct and staged runners. Compare at the same
accepted cut, not merely the same window timestamp. Staged equality applies
only when the intermediate representation retains what the parent needs:
for example, totals add, but a mean needs both sum and population. Use exact
comparisons for integer fixtures; specify a numeric error bound for each
floating-point fixture that permits different summation orders. Timestamps,
IDs, counts, flags and completeness always compare exactly.

## First acceptance script

| Operation | Expected observation |
| --- | --- |
| Observe cumulative `api/A=900` with unknown start | Establish a baseline; no increase of 900. |
| Observe `api/A=907` in the same epoch, seal the minute | Service increment 7. |
| Read that commit twice, then reopen at its input cut | Same 7, same epoch, no additional publication key. |
| Deliver the sealed delta of 7 to B; lose the ACK and retry | At its aligned boundary B includes 7 once, not 0 or 14. |

Extend the corpus with the boundary and rejection cases from [A2](a2.md)
and the operational matrix in [F3](f3.md). The reference interpreter, a
query-time evaluator and Prometheus only share expected answers on the
semantics each actually implements.
