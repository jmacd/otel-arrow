# E2. Serve committed pipeline data over HTTP pull

[Worklist](../metrics-transducer-worklist.md) | Depends on A1 and D4.

The server **receives a GET and exports data in the response**. It does
not accept pushed telemetry, contact scrape targets or expose the engine's
[admin metrics][admin]. Prometheus is the first client, not the server's
data model. A route can serve any configured signal for which its selected
encoder produces a wire-compatible HTTP body.

## Route contract

Configure a path, signal, read-only snapshot source and ordered offers. An
offer binds a media type and its parameters to a registered byte encoding.
Resolve each [encoding plan][plan] against the pipeline's [codec bindings]
at startup. Reject an unknown encoding, a decode-only binding, a signal
mismatch or an ambiguous media-type mapping. Native OTAP is a processing
representation, not an offer. The HTTP server owns negotiation, access
controls, timeouts and transport compression; codecs own the body format.

1. For a known route, select an acceptable offer by HTTP `Accept`, including
   media ranges, parameters and quality weights. Honor exclusions (`q=0`);
   break ties by configured order. No preference selects the default. No
   match returns `406 Not Acceptable` rather than a mislabeled fallback.
2. Pin one committed snapshot P and obtain the selected representation.
   Forward already compatible bytes if policy permits; otherwise encode via
   the pipeline service. Return the offer's `Content-Type` and `Vary: Accept`.
   A response must be one valid body, not an arbitrary concatenation of
   independently encoded batches.
3. Bound concurrent reads, encoding work, retained snapshot bytes, response
   size and time spent on slow clients. Refuse an over-budget request rather
   than return a truncated success. Release P on completion or cancellation.
   No GET advances a cursor, drains data, seals a window or triggers a flush.
   A concurrent commit becomes visible to subsequent reads, not halfway
   through an existing response.

## Interoperability examples

Configure `/metrics` for Prometheus text 0.0.4 and OpenMetrics text 1.0.
Their proposed codecs translate metric names, unit suffixes and labels;
reject collisions after translation rather than merging distinct series.
Expose a cumulative monotonic sum as a counter and a non-monotonic sum as
a gauge without changing its additive meaning in storage. Omit a stale
series from the current scrape, not as a numeric zero. Format-specific
timestamps (e.g., milliseconds in Prometheus text versus seconds in
OpenMetrics) and the OpenMetrics end marker belong in the codec.

At commit P let `requests` total 7 for `service=api`. Scrape with the
[existing receiver][scraper] and an independent Prometheus parser or server:
both should see `requests_total{service="api"} 7`. Select each text format
in turn and check the returned type. Concurrent GETs at P see 7; a push
reader's unacknowledged publication is still pending.

At the same P, configure `/snapshot/metrics` with the [OTLP bytes codec]
and `application/x-protobuf`. Decode the body as an OTLP metrics service
request and compare its labeled sum, temporality and boundary against P.
This GET is not the OTLP/HTTP ingestion protocol. Requesting only protobuf
on the text-only `/metrics` route returns 406. A snapshot source of traces
could use the same server and `otlp-bytes` binding on a traces route; only
the route's signal, source and offers must agree.
