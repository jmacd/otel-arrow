# B3. Prove a bookmarked suffix survives reclamation and crashes

[Worklist](../metrics-transducer-worklist.md) | [Deletion rules](b2.md)

The oracle is the **content of the suffix**, not a segment count, a memory
mapping, or successful return from open. Give each test bundle an ordinal
and known Arrow values. Keep expected ordinals and value digests outside the
store; reopen and read them using the proposed bookmark scan. Do not keep
Arrow bundles alive across phases.

## Reproducible pressure fixture

1. Use an isolated store, one ordinary subscriber and explicit finalization
   to put a known bundle in each segment 0 through 90. Register two bookmarks
   at creation, then authorize advances to 42 and 60. ACK deliveries through
   90, flush subscriber progress and release every claim. Verify an
   independent scan up to 90 did not change either bookmark.
2. Enable completed cleanup, inject expired file ages and reopen under a
   finite disk budget. Exercise startup expiry, live expiry and forced
   `drop_oldest`, including a deferred deletion retry. At each barrier, read
   **every** payload in 42 through 90 in order. With only protected files
   left, admission that needs reclamation must return capacity, not report a
   dropped bundle. Use an explicit full-budget condition, not timing.
3. Advance the first bookmark to 75. With all deliveries complete, maintenance
   now reclaims 42 through 59. Admit a small previously blocked append and
   read 60 successfully. Keep the subscriber pending on a new
   segment and confirm normal completed cleanup still honors it after both
   bookmarks pass it. Repeat with a durable WAL-only tail: interrupt before
   finalization, reopen past the age cutoff, and verify that tail once, in
   addition to the retained segments.

## Interrupting metadata publication

Use the [engine's reopen and pressure fixtures][engine] and the
[WAL writer's sidecar fault hook][wal] as precedents. Add bookmark-specific
failpoints and a filesystem model that distinguishes rename visibility from
directory durability. Interrupt create, advance and retire before and after
file sync, rename and directory sync, without graceful shutdown. No input is
promised under a registration that never became durable. For an authorized
advance from 42 to 61, a restart may recover the old or the new whole record
at the rename boundary; no successful advance may revert after its final
barrier. In either case all segments still needed by the consumer's durable
checkpoint must read back. An interrupted retirement cannot release data
before the owner has durably relinquished its need.

Remove a required segment, flip a registry checksum and damage an accepted
WAL frame in separate runs. Each must prevent new admission and destructive
maintenance with a specific recovery error. No wall-clock sleeps, clean
shutdown flushes masquerading as crashes, or reliance on an OS file lock.
