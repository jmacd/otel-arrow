# Request Metadata Context

**Status:** Draft

## Overview

A **metadata context** is request-scoped metadata attached to an
`OtapPdata` and carried through the pipeline. We use a policy
declaration language consisting of **context keys** holding individual
values including transport headers, authorized identity fields, and
other contextual information (e.g. peer IP address, idempotency key,
constants) and **identities** consisting of a set of specific keys.

A **metadata compiler** computes a set of tables describing the engine
configuration, containing information needed by:

- **extractors** which configure how to form a context key from a carrier
- **injectors** which configure how to place a context key into a carrier
- **propagators** which can parition or condition by identities and keys.

Users of the metadata context interface will bind specific mechanisms,
for receivers to obtain extactors, for exporters to obtain injectors,
and propagators to get a parition function, a condition set evaluator,
and so on.

## Configuration model

### Extractors

Extractors can express a variety of actions to take while building new
context. Extractors appear in the `policies::context` map, with
structure as follows:

```yaml
policies:
  context:
    <key>:
      extract: <extractor>
```

For example, a transport header extractor:

```yaml
transport_header: x-request-id
```

or an authorized identity extractor:

```yaml
authorized_claim: tenant_id
```

The list of extractors will be extended as needed. For example, we may
add `randomness` for attaching randomness to a request (e.g.,
idemdpotency key), `generic_key` for attaching static or constant
information (e.g., route name).

Extractors can also be conditional, for example:

```yaml
transport_header_match:
  header: x-environment
  values: [production, staging]
```

We can add new extractors, for example to take the first in a list of
header names:

```yaml
transport_headers: [x-request-id, x-legacy-id]
```

### Identities

The identity is a set of context keys configured from the available
extractors. An identity is formed when all of the specified context
key extractors succeed.

```yaml
policies:
  identity:
    <name>:
      fields: [<key>, ...]
      inject: [<identity_injector>, ...]
```

Injectors for identities apply to their set of context keys.

```yaml
policies:
  identity:
    customer
      fields: [key1, key2]
      inject: 
      - { transport_header: x-identity, constant: customer }
      - { transport_header: x-customer, format: "{key1}/{key2}" }
```

### Injectors

Injectors appear alongside extractors for a context key, configuring
how to reverse the operation.

```yaml
policies:
  context:
    <key>:
      inject: <injector>
```

For injecting transport header into outgoing requests, the injector
configuration matches the corresponding extractor:

```yaml
transport_header: x-request-id
```

### Ingress policies

The engine features a policy section allowing the user to declare
which identities are required by a node.

```yaml
policies:
  ingress:
    required: [<identity>, ...]
```

## Examples

### Example 1: propagate a request header

A header can be forwarded with the identical name:

```yaml
policies:
  context:
    request_id:
      extract: {transport_header: x-request-id}
      inject: {transport_header: x-request-id}
```

or mapped to a new name:

```yaml
policies:
  context:
    request_id:
      extract: {transport_header: x-request-id}
      inject: {transport_header: x-external-id}
```

The rest of the engine configuration is unmodified for this example.

The combination of extractors and injectors replaces `header_capture`
and `header_propagation` using context keys. This mechanism can
translate authorized identity and other non-transport-header keys into
outgoing transport headers, for example.

### Example 2: authenticated tenants

Here we use two authorized claims and a constant value as context
keys. An identity named "customer" is defined combining tenant and
project identifiers. The policies in this example:

```yaml
policies:
  context:
    tenant_id:
      extract: {authorized_claim: tenant_id}
      inject:  {transport_header: x-customer-id}
    project_id:
      extract: {authorized_claim: project_id}
      inject:  {transport_header: x-workspace-id}
    origin:
      extract: {constant: edge-us-west}
      inject:  {transport_header: x-origin}

  identity:
    customer:
      keys: [tenant_id, project_id]
      inject: {transport_header: x-identity, constant: customer}

  ingress:
    required: [customer]
```

Receivers and exporters automatically bind their extractors and
injectors. In the example, only the batch processor explicitly
configures the context key that it uses for partitioning.

```yaml
groups:
  default:
    pipelines:
      main:
        extensions:
          # ...
        nodes:
          ingest:
            # ...
          batch:
            type: processor:batch
            config:
              # ...
              partition:
                by: {identity: customer}
                # ...
          backend:
            # ...
```

### Example 3: a tenant-aware rate limiter

Here we extend the engine's rate limiter policies with identity-based
conditions.

```yaml
policies:
  context:
    tenant_id:  {extract: {authorized_claim: tenant_id}}
    project_id: {extract: {authorized_claim: project_id}}

  identity:
    customer:
      keys: [tenant_id, project_id]
  
  ingress:
    required: [customer]

  resources:
    rate_limiters:
      ingest:
        unit: size_bytes
        token_bucket: {allow: 200MiB, interval: 1s}
        conditions:
          - entries:
              - {key: tenant_id, value: acme}
              - {key: project_id}
          - entries:
              - {key: tenant_id}
              - {key: project_id}
            token_bucket: {allow: 10MiB, interval: 1s}

groups:
  default:
    pipelines:
      main:
        nodes:
          ingest:
            type: receiver:otlp
            rate_limiters: [ingest]
            policies:
              ingress:
                required: [customer]
            config:
              protocols:
                grpc:
                  listening_addr: 0.0.0.0:4317
```

This approach can also be applied to select conditional configuration
for a node based on identity. For example:

```yaml
batch:
  type: processor:batch
  config:
    # ...
    partitions:
      - entries:
          - {key: tenant_id, value: acme}
          - {key: project_id}
        token_bucket: {allow: 32MiB, interval: 1s}
      - entries:
          - {key: tenant_id}
          - {key: project_id}
        token_bucket: {allow: 16MiB, interval: 1s}
```

## Example 4: crossing a topic boundary

A topic decouples pipelines, so the context has to be rebuilt on the
far side.  The boundary declares will cross, including identities and
individual keys.

```yaml
topics:
  authenticated_signals:
    backend: in_memory
    context:
      carry:
        identities: [customer]
        keys: [request_id]
```

## Bindings

Every place a node or a boundary refers to metadata is one of a small, closed
set of forms. This is the whole configuration surface.

| Binding | Operates on | Declared at | Example |
|---|---|---|---|
| extractor | key | `policies.context.<key>.extract` | Examples 1, 2 |
| injector | key or identity | `policies.context.<key>.inject`, `policies.identity.<id>.inject` | Examples 1, 2 |
| requirement | identity | node `policies.ingress.required` | Examples 2, 3 |
| partitioner | identity | node config | `batch.partition.by` |
| carry | identity and key | topic declaration | Example 4 |
| condition | key sequence | node config | Example 3 `limits[].entries` |

Two rules keep this small.

**A node names what it does with metadata, in the field describing the use.**
There is no generic binding namespace. This follows Envoy, which binds by
position: a filter applies where it is placed and a route's descriptors are
written on the route. `partition: {by: {identity: customer}}` and
`ingress.required` are the same idea.

**A key is unqualified until it is ambiguous.** `{key: tenant_id}` is accepted
wherever exactly one identity declared by that consumer produces it. When
several do, the compiler fails with an error naming the candidates and the
caller writes `{identity: customer, key: tenant_id}`. There is no precedence
rule that silently picks one, because that is how an untrusted header would
come to shadow an authorized claim.

## Options: absent, unmatched, and default

Envoy has a precise vocabulary for what happens when an input is missing, a
match fails, or nothing matches. We adopt its names wherever the behaviour is
the same, so that an operator who knows Envoy needs no translation table.

### When an input is missing

| Envoy option | Where | Default | Effect |
|---|---|---|---|
| `skip_if_absent` | `RequestHeaders`, `MetaData`, `QueryParameters` | `false` | `false`: the action fails, abandoning the whole descriptor. `true`: the action succeeds and contributes no entry |
| `default_value` | `MetaData` | unset | substitute this value when the input is empty; an entry is produced |
| `on_header_missing` | `header_to_metadata` | unset | the capture-side spelling of `default_value` |

`skip_if_absent: false` is the default, so absence is fatal to the identity
unless the operator says otherwise. That is the behaviour our extractors have
today.

### When a match fails

| Envoy option | Where | Default | Effect |
|---|---|---|---|
| `expect_match` | `HeaderValueMatch`, `QueryParameterValueMatch` | `true` | inverts the test, so a descriptor can be produced *because* a header is absent or differs |
| `invert_match` | `RemoteAddressMatch.address_matcher` | `false` | the same idea for address ranges |

A failed match returns false and abandons the descriptor. There is deliberately
no fallback value: to express "premium when gold, standard otherwise" Envoy
uses two descriptors with complementary `expect_match`, which is two identities
here.

### When a value formats to empty

| Envoy option | Where | Default | Effect |
|---|---|---|---|
| `default_value` | `GenericKey`, `HeaderValueMatch` | unset | used when the substituted `descriptor_value` is empty. With no default, the entry is skipped and the descriptor survives |

This applies only where `descriptor_value` is treated as a substitution format
string, which Envoy gates behind a runtime feature. It is unrelated to
matching.

### When nothing matches at the limiter

| Envoy option | Where | Default | Effect |
|---|---|---|---|
| `always_consume_default_token_bucket` | local rate limit | `true` | consume the default bucket even when a descriptor matched |
| `shadow_mode` | per descriptor | `false` | count the decision but do not enforce it |
| `max_dynamic_descriptors` | local rate limit | `20` | LRU bound on buckets created by wildcard descriptors |

`shadow_mode` is how a limit is rolled out safely, and `max_dynamic_descriptors`
is what keeps a wildcard over an unbounded key space from growing without
bound. Both matter to us for the same reasons.

### When the limiter itself fails

| Envoy option | Where | Default | Effect |
|---|---|---|---|
| `failure_mode_deny` | global rate limit filter | `false` | fail open by default; set to fail closed |
| `rate_limited_as_resource_exhausted` | global rate limit filter | `false` | choose the gRPC status used on refusal |

### When injecting onto an existing header

| Envoy option | Where | Default | Effect |
|---|---|---|---|
| `append_action` | `HeaderValueOption` | `APPEND_IF_EXISTS_OR_ADD` | also `ADD_IF_ABSENT`, `OVERWRITE_IF_EXISTS_OR_ADD`, `OVERWRITE_IF_EXISTS` |
| `keep_empty_value` | `HeaderValueOption` | `false` | whether an empty formatted value still emits the header |

Our OTLP exporter currently hard-codes one of these -- a statically configured
credential wins over a propagated header, which is `ADD_IF_ABSENT`. It should
be a per-injector option under Envoy's name.

### When scopes overlap

| Envoy option | Where | Effect |
|---|---|---|
| `vh_rate_limits` | rate limit per route | `INCLUDE`, `IGNORE`, or `OVERRIDE` virtual-host policy |
| `most_specific_header_mutations_wins` | `header_mutation` | choose the direction of specificity |

The lesson is that Envoy never silently deep-merges scoped configuration: it
replaces, and inheritance is an explicit named choice at the point of use. Our
policy scopes should say the same.

### Shape variation is expressed as identities, not as optional keys

One consequence of `skip_if_absent` deserves its own statement, because it
decides how much of this we take.

A descriptor whose entry was skipped is *shorter*, and Envoy's
`matchDescriptorEntries` requires the request and configured entry counts to be
equal. A skipped entry therefore does not merely omit a value -- it changes
which conditions the descriptor can match at all. An identity with `n` optional
keys can produce up to `2^n` shapes.

Our compiler gives each identity one fixed, ordered key sequence, which is what
keeps the signature space small and lets a condition bind at compile time. We
propose to keep that and to **not** adopt `skip_if_absent`, requiring instead
that each shape be declared as its own identity:

```yaml
  identity:
    customer:
      keys: [tenant_id, project_id]
    tenant:
      keys: [tenant_id]
```

This is the same rule already used for classification, where two mutually
exclusive labels are two identities rather than one switching key. Stating it
once: **variation in shape is variation in identity.** `default_value` remains
available and is adopted, because substituting a value does not change shape.

The cost is that an operator who wants "with project, or without" writes two
identities instead of one flag. The benefit is that every identity has a fixed
sequence, every condition binds statically, error messages name concrete
identities, and the compiler's bounds stay small.

## What is compiled

`MetadataCompiler::compile` produces one immutable artifact per epoch.

1. **Validate** everything, collecting all errors rather than the first, so a
   misconfigured engine explains itself in one pass.
2. **Reachability**, at two levels. Globally, drop keys, identities, and
   extractors that no reachable consumer observes, and report each drop so an
   operator learns at startup that a configured header goes nowhere. Per
   producer, restrict to the consumers that producer can reach, which becomes
   its extraction plan: a receiver feeding one exporter does not pay for an
   identity that only a distant router matches on. Plans prune *work*, never
   *layout*, so every identifier means the same thing everywhere and a context
   crosses node boundaries unchanged.
3. **Intern** wire names and literals. A name lookup is one allocation-free
   probe. Each literal becomes a dictionary symbol; a value no condition
   declared encodes to a reserved unknown symbol and matches nothing.
4. **Derive signatures** by dropping wildcards from conditions, and give every
   compatible (identity, signature) pair one compact lookup word.
5. **Build branch tables** indexed directly by that word.
6. **Fix retention and layout.** Only keys whose values are not already known
   at compile time are retained; a key sourced from constants needs only its
   symbol.

The pipeline graph reaches the compiler only as an opaque producer-to-consumer
relation, so the compiler has no pipeline or engine dependency and holds no
configuration syntax. Policy is translated into declarations by a separate
adapter.

## The packed context

A context carries **matching inputs, not matching answers**:

```text
offset  region              bytes
0       epoch               4
        layout fingerprint  8
        resolved identities ceil(identities / 8)
        symbol field        ceil(sum of symbol widths / 8)
        region index        2 x (regions + 1)
        data                retained values
```

A producer resolves identities, dictionary-encodes each value-matched key once,
and writes the result. A consumer that is actually reached assembles its lookup
words from those symbols and reads its own branch tables. This mirrors Envoy,
where the filter builds descriptors and the limiter that is reached performs
the lookup.

Three properties follow, and they are the reason for the arrangement:

- **Work follows the path.** A request reaching one limiter pays that limiter's
  table reads, not every limiter in the engine. Static analysis cannot achieve
  this, because which identities resolve is a request-time fact.
- **Size tracks the data model, not the pipeline.** The symbol field has one
  field per value-matched extractor. Precomputed answers would instead need one
  field per condition set, growing with every node added.
- **Condition answers never enter the context**, so a new epoch may change
  conditions without adding per-request fields.

The layout fingerprint is carried beside the epoch because epochs are
operational counters that can be reused after a restart; the fingerprint keeps
such reuse from letting old bytes be read against a new layout.

Matching is exact. Hashing only ever finds a candidate, which is then compared
byte for byte, so a hash collision cannot cause a cross-tenant match.

## Live reconfiguration

Producer and consumer configuration are compiled together, so a change on
either side compiles a new epoch. Consumers are reconfigured ahead of
producers. A context carries the epoch that built it; a consumer holding a
different epoch fails the request rather than reading a slot that has moved.

Several epochs can therefore be live at once, and components that hold
in-flight data must keep the epoch that built it for as long as they hold it.
Data that must outlive an epoch -- durable buffers, topics -- is written in the
canonical boundary form instead, per Example 4.

## Performance invariants

Every dimension is explicitly bounded, and exceeding a bound is a configuration
error rather than an allocation: keys, extractors, identities, keys per
identity, names per extractor, condition sets, entries per set, signatures,
lookup-word width, branch-table entries, dictionary entries per key, literal
bytes, value bytes, values per key, retained values, context bytes, scratch
bytes, producers, and consumers.

- A context costs no allocation when nothing resolves, and one allocation
  otherwise; cloning is a refcount increment.
- Construction scratch is reused per producer and does not allocate at steady
  state.
- Compiled state is immutable within an epoch, so construction and lookups take
  no locks and every per-core pipeline shares one copy.
- A consumer's work is bounded by its own declared identities and conditions,
  not by the size of the engine.

## Migration from transport headers

The existing configuration compiles into this model without behaviour change.

| Existing | Becomes |
|---|---|
| `match_names: [a, b]` with `store_as: f` | one extractor per name producing key `f`, one identity each |
| `selector: all_captured` | an injector per extracted key |
| `selector: {type: named, named: [f]}` | an injector for `f` |
| override `action: drop` | no injector |
| `name: preserve` | injector name equals that extractor's name |
| `name: stored_name` | injector name equals the key name |
| capture limits and counters | extractor limits, same drop-and-count behaviour |

Two existing behaviours are worth calling out because they differ from Envoy.
We forward no inbound header unless an injector says to, so we need no `remove`
rule and "propagate nothing" is the safe default. And receivers already receive
protocol-canonical header names from their transports, so there is no original
casing to preserve.

## Open questions

- **Extractor placement.** An extractor declared under a key is the right shape
  for the one-to-one case, but a key with different sources in different
  identities needs the extractor declared under the identity, which is where
  Envoy puts its actions. Supporting both is probably right; the RFC should
  settle the spelling.
- **The third extractor outcome.** Envoy's `skip_if_absent` lets an action
  succeed while contributing no entry. We propose not to adopt it, because it
  makes an identity's shape variable; see "Shape variation is expressed as
  identities". `default_value` we do adopt. If the two-identity spelling proves
  too heavy in practice, this is the decision to revisit.
- **Namespaces.** Envoy addresses metadata as `namespace:key`. A namespace
  would separate raw header keys from verified claim keys in the name itself.
  Our key space is currently flat.
- **Value expressions.** Envoy's descriptor values may be substitution format
  strings, and the same formatter drives header injection. Adopting one small
  expression language on both sides is attractive and out of scope here.
